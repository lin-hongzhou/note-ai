# 产品探索结论：个人效率与个人财务管理应用

> **状态：探索结论，尚未进入实施。**
>
> 本文沉淀当前已确认的产品需求、边界和待验证假设。它不是 Trellis task、技术方案、接口设计或开发计划；后续产品讨论可以推翻或补充其中任何结论。

## 1. 产品问题

现有备忘录能让用户快速记下内容，却容易让较早的计划沉入时间线。用户在事情多时能记录住事项，但过去没有完成、又没有重新查看的计划可能从此失去；同时，日常消费虽可零散记下，却缺少稳定、可信的个人回顾。

本产品不依赖小米备忘录，也不是其插件或数据同步层。它应是一个独立、跨平台的个人效率与个人财务管理产品，帮助用户：

1. 随时安全记录；
2. 每天看到当前重点；
3. 每周重新判断旧计划是推进、暂缓还是放弃；
4. 看清**已记录**的钱从哪里来、花到哪里去。

## 2. 产品承诺与核心循环

### 产品承诺

> 用户可随时安全记录；每天能看到重点；每周能做出取舍；并能从已记录账目中理解自己的收支去向。

其中最核心的承诺是：

> **每周回顾并做决定，而不是逼用户完成所有旧计划。**

“暂缓”和“不再需要”是积极、正常的结果。系统只能提出回顾和建议，不能在未经用户同意时把“以后想做”自动排入日程。

### 核心使用循环

```text
平时：快速捕捉
  ↓
每天：通过 Android 今日概览或小组件看到重点、完成待办、快速记账
  ↓
每周：在 Web 或 Android 回顾计划与消费，决定推进、保留、暂缓或放弃
  ↓
下一周：带着 1–3 件真正重要的事项继续行动
```

## 3. 目标用户与首轮验证

### 首要用户

第一批要验证的用户是：以 Android 为主、在碎片时间记录个人计划、临时想法和日常收支的人。他们会使用手机快速捕捉，并愿意在桌面 Web 端集中整理、搜索和回顾。

职场人士和学生可以作为少量试用者参与验证，但首轮不应为其预先增加工作协作、课程管理等专属功能。

### Alpha 验证假设

在约四周的邀请制 Alpha 中，产品要验证的不是“功能是否齐全”，而是：

- 用户是否愿意把需要行动、核对或回顾的内容优先记入本产品；
- 用户是否会每天查看今日概览或桌面小组件；
- 用户是否会完成全部或部分每周回顾；
- 用户是否会重新发现并处理至少一件原本会沉底的计划；
- 用户是否能从已记录收支中得到实际的消费认识；
- Android 捕捉与 Web 整理/回顾的分工是否自然。

## 4. 产品边界

### 三个独立业务系统

```text
独立产品
├─ 待办系统
│  ├─ 已安排 / 今日行动
│  └─ 以后想做
├─ 记账系统
└─ 笔记系统
```

三者共享快速捕捉体验，但不应被混成一个不清晰的“万能记录列表”。

### 明确不做或不在首轮承诺的能力

- 不做小米备忘录插件、依赖其接口或向其反向同步数据；
- 不做完整项目管理（子任务、依赖、时间块、甘特图等）；
- 不做完整知识库或笔记软件替代品；
- 不做多人协作、共享待办、家庭账本或团队工作空间；
- 不做银行余额、正式资金账户、转账、对账；
- 不承诺自动获取全部消费，也不把统计表述为用户的全部财务现实；
- 不让普通用户选择 GPT、DeepSeek、豆包等底层模型供应商；
- 不在邀请制 Alpha 阶段优先做订阅、自动账单同步或复杂运营后台。

## 5. 待办系统

### 待办与“以后想做”

待办是可执行、可完成的一步行动。它可以具有计划时间、截止时间和优先级，两种时间均可为空。

“以后想做”属于待办模块，用于未承诺具体行动时间的愿望或计划。它不会被自动安排、自动催促或自动转为日程；它应在回顾中有机会重新出现。

### 优先级与今日排序（已确认：方案 B）

待办采用三档、可由用户随时修改的优先级：**高 / 普通 / 低**；新建待办默认“普通”。优先级表达用户判断的事项重要性，不能与计划时间、截止时间混为同一个概念。

“今日重点”、待办列表和小组件需要同时考虑时间状态与优先级，默认推荐顺序为：

1. 已逾期的待办；
2. 今天具有截止时间或计划时间的待办；
3. 未安排时间但标记为高优先级的待办；
4. 普通优先级待办；
5. 低优先级待办。

界面应说明推荐原因，例如“今天 18:00 截止”或“你标记为高优先级”。系统不自动判定待办的重要性；高优先级是用户的个人判断，而不是系统授予的评价。

### 每周回顾

每周回顾采用**用户可调整的默认回顾窗口 + 一次温和提醒 + 自动顺延**：首次使用时提供推荐的每周回顾时间，用户可自行修改。到达窗口时只发送一次提醒；如果用户未完成或选择跳过，首页保留“本周回顾待开始”的轻提示，不重复催促。未处理内容会自然并入下一次回顾，跳过不被视为失败。

每周回顾是一个可跳过、约 5–10 分钟的引导式流程，应帮助用户：

1. 处理未完成待办：安排、延期或放弃；
2. 从“以后想做”中选择推进、保留、减少出现或放弃；
3. 查看本周收入、支出、结余和主要消费去向；
4. 选出下周最重要的 1–3 件事。

回顾不应一次展示全部积压内容，也不应把用户推入完成焦虑。

### 回顾推荐规则（已确认：方案 D）

对“以后想做”，采用**透明规则排序 + 轻量轮换 + 用户控制**：

1. 用户标记为“近期想推进”的计划优先；
2. 轮换展示较久未回顾的计划；
3. 用户选择“以后再看”后，在一段时间内降低出现频率；
4. 用户选择“减少出现”后，拉长再次出现间隔；
5. 用户选择“不再需要”后，归档且不再推荐；
6. 每条推荐说明理由，例如“已 45 天未回顾”或“你标记为近期想推进”；
7. 用户可替换推荐、搜索并加入本周回顾，以及调整可见度。

原则是：系统负责让遗忘的计划重新拥有被看见的机会；用户负责判断它是否仍然重要。

## 6. 记账系统

首期承诺：

> 快速、可信地记录每笔收入和支出，并通过日、周、月和分类回顾，让用户看清已记录的钱从哪里来、花到哪里去。

一笔已确认账目至少包含：收支方向、金额、发生时间、分类、备注；支付方式可选，包含现金、微信支付、支付宝、银行卡、信用卡等。

分类使用少量清晰的内置标准分类，并允许用户新增自定义分类。系统或 AI 可以提出分类建议，只有用户确认后才作为正式结果保存。

首期不把支付方式实现为正式账户，也不计算账户余额、转账或对账。后续演进可依次考虑：用户主动导入账单、待确认账目、去重/合并，以及在合法、稳定、明确授权条件下评估自动同步。

### 值得查看的收支变化（已确认：方案 B）

在周/月回顾中，产品可以提供“**值得查看的收支变化**”，但只使用透明、可解释的规则，不给消费行为作价值判断。例如：

- 某一分类的已记录支出相比过去四周平均高出一定比例；
- 某笔账目金额高于用户近三个月同分类已记录账目的常见范围；
- 本月出现此前较少使用的账目分类。

每条提示必须说明：它仅基于**已记录账目**、所采用的对比范围和触发原因。数据不足时不生成提示；不得使用“异常”“浪费”“不合理”等文案；用户可以关闭此类提示。首期不做基于完整财务历史的 AI 自动解读，也不以预算超额作为核心机制。

## 7. 笔记系统

笔记是独立的轻量记录系统，按时间线与搜索为主；笔记类型、可选标签、收藏和“稍后回顾”仅作为轻量组织工具。用户不需要先建立文件夹或笔记本。

笔记支持文本输入和语音转写文本。其基本流程是：

```text
语音 → 转写文本 → 用户查看/修改/确认 → 文本原样保存为笔记正文
```

AI 不得擅自改写笔记正文。只有用户主动请求时，AI 才可基于当前笔记建议标题、类型、标签或提取行动项。

从笔记创建待办或“以后想做”时，应创建新的待办/计划、保留原笔记正文，并建立双方关联。

### 笔记检索（已确认：方案 B）

首期笔记检索以“时间线 + 搜索”为主，支持：

- 关键词搜索笔记正文与标题；
- 时间范围筛选，例如今天、近 7 天、本月和自定义范围；
- 笔记类型筛选；
- 收藏与“稍后回顾”的快捷筛选。

标签可以保留为轻量元信息，但首期不把复杂标签体系作为检索核心；不做语义搜索、AI 问答式检索、保存搜索条件或笔记本/文件夹体系。

## 8. 快速捕捉、AI 与语音

首页同时提供明确的功能入口与智能快速入口：

```text
[记一笔] [加待办] [写笔记]
[语音 / 文本智能快速记录]
```

| 用户入口 | 默认处理 | 正式保存前的保障 |
| --- | --- | --- |
| 记一笔 | 提取收支、金额、时间、分类等字段 | 用户确认，确保账目正确 |
| 加待办 | 提炼可执行事项、计划/截止时间、优先级 | 用户确认，确保表述可执行 |
| 写笔记 | 原样保存内容 | 默认不将正文交给大模型 |
| 智能快速记录 | 建议归类为待办、账目或笔记 | 进入待确认收件箱 |
| 无法判断 | 不强制分类 | 保留原文，允许稍后处理 |

### AI 使用规则

- 基础记录能力不得依赖 AI；用户关闭 AI 后仍可记录、同步、使用回收站和查看基础统计；
- 对记账和待办，只发送当前一次提交的文本，用于给出结构化建议；
- 笔记默认不发送给大模型；用户主动请求辅助时，才发送当前笔记；
- 智能快速入口只有在用户主动选择“智能整理”后，才发送当前文本；
- 个性化学习优先以服务端保存的、来自用户已确认结构化结果的偏好规则实现；
- 不把完整历史原文持续发送给第三方模型；历史偏好只以受控、最小化的建议上下文使用；
- 用户能查看、修正、关闭或清除个性化偏好；
- 模型供应商由平台统一管理，普通用户只设置 AI 是否启用、偏好更快或更准确等结果偏好。

### 语音规则

- Android 在线时支持普通话和英语的语音转写；
- 语音转写成功前，录音只能加密保存于 Android 应用私有存储的临时区，不上传至同步数据库、不对多设备同步、不作为音频存档；
- 网络或转写失败时，用户可使用这份本地临时音频稍后重试转写，或放弃语音并改为手动文本草稿；转写成功、用户主动放弃或请求取消时，必须立即删除该音频；
- 未处理的临时音频最长保留 **24 小时**。创建时必须显示确切到期时间和处理选项；在剩余 12 小时和 1 小时时，如用户允许通知，发送本地通知，否则至少在应用内持续显示待处理状态；
- 用户在到期前可重试转写、改为手动文本或立即删除。若用户未处理，到期时自动且不可恢复地删除本地音频；删除后仅保留不含音频或转写文本的状态提示（例如“语音草稿已过期删除”），便于用户知晓发生的事情；
- 因转写尚未完成而被清除的本地音频，不进入 30 天业务回收站，也不能恢复；回收站仅用于已经形成的待办、账目和笔记业务数据。
- 服务端与第三方转写服务仅可在本次转写处理期间使用音频，不保留可用于重试、同步或人工查看的服务端副本；
- 离线阶段不承诺把新录音转为文本；
- Web Alpha 不要求完整浏览器语音输入链路。

## 9. 平台体验

| 平台 | 核心角色 |
| --- | --- |
| Android App | 随手记录、在线语音输入、查看今日重点、完成行动、桌面小组件、离线保存 |
| Web 用户端 | 集中整理、每周回顾、财务分析、搜索筛选、数据导出、账户设置 |
| 运营管理控制台（后续） | 模型提供商、成本与额度、账号风险、订阅和运营配置 |

Android 是“随手记录与当下行动端”；Web 是“集中整理、规划与数据回顾端”。两端都能完成核心数据操作，但复杂分析和批量管理在 Web 端更深入。

### 今日概览与小组件

默认首页为今日概览，但 Android 与 Web 不复制同一布局：Android 突出快速入口、重点待办、今日进度和基础收支；Web 是可行动的数据工作台，不能成为只读报表墙。

Android 小组件是被动可见的信息面板，可展示高优先级待办、今日待办数、今日或本月收入/支出/结余、待回顾计划数和快捷入口。首期采用预设模板，默认隐藏敏感待办标题与财务金额；用户首次添加每个小组件时，需获得清晰的隐私展示引导，并可仅为该组件开启详情。

### 提醒

- 只提醒用户明确设置计划时间或截止时间的待办；
- “以后想做”只通过每周或每月回顾温和出现；
- 普通笔记不主动提醒，除非用户自行标记“稍后回顾”；
- 账目不逐笔提醒，只在用户允许时提供周/月回顾；
- 用户可关闭提醒并设置通知时段。

## 10. 数据所有权、安全与同步

### 数据范围

首期仅支持个人私有数据与同账号多设备同步。用户通过邮箱和密码注册、验证邮箱、登录、找回或重设密码；OAuth、Passkey 和游客模式留待后续评估。

### 离线与同步承诺

> 无论是否联网，用户都能先安全记录；联网后再完成同步与 AI 整理。

Android 离线时可保存待办、笔记、账目草稿和修改操作，并能查看最近同步的数据。产品应让用户看到待同步、同步失败与可重试状态；联网后同步，并将需要 AI 整理的内容放入待确认流程。

若多设备发生无法安全合并的并发修改，系统必须保留两个版本、创建待处理冲突并让用户选择或手工合并；不得静默覆盖笔记原文、账目金额或待办安排。

### 删除、恢复与导出

- 删除内容默认进入回收站，保留 30 天，用户可恢复或立即永久删除；
- 历史版本保留最近 10 个版本或 90 天，以先达到者为准；
- 用户可从 Web 导出账目（CSV、JSON）及待办、计划、笔记、关联、分类、标签等（JSON；笔记可附 Markdown）；
- 导出包不包含密码哈希、令牌、模型凭据和内部审计细节；下载链接应短时有效；
- 用户可自行发起账号删除。申请立即停用账号、撤销所有设备会话、停止同步和 AI 处理；30 天内可撤销，到期后清除可识别账户与业务数据，并按公开周期清理备份残留。

## 11. 版本策略

当前优先目标是以最快速度推出能够验证核心习惯循环的第一版（V1），而不是一次性完成全部设想。V1 必须形成“Android 快速捕捉 → 同账号同步 → Web 整理/每周回顾 → Android 继续行动”的可验证闭环；任何不直接支撑该闭环、会显著增加实现或运维复杂度的能力，应在后续迭代验证后再加入。

### V1 范围边界（已确认：方案 B）

V1 采用“闭环型首发”：待办、记账和笔记三项能力都必须可用，但每项只交付一条最短、可靠、可被真实用户验证的路径。V1 的目标不是展示全部设想，而是让受邀 Alpha 用户连续使用约四周，验证是否形成核心习惯循环。Alpha 可以从 3–5 位相似用户开始；在没有数据安全或可靠性阻断问题后，可分批扩大到数十甚至数百位受邀用户。

**V1 必须交付：**

1. **账户与同步**：邮箱/密码登录；同账号 Android 与 Web 同步；Android 离线先保存文本内容、联网后同步；可见的同步中、失败和重试状态。
2. **待办**：创建、编辑、完成、放弃；高/普通/低优先级；计划时间和截止时间；“以后想做”；简化可用的每周回顾；Android 今日重点和一个基础小组件模板。
3. **记账**：收入/支出记录；金额、时间、分类、备注和可选支付方式；日/周/月基础统计与分类汇总；每周回顾中的本周收支；少量透明规则驱动的“值得查看的收支变化”。
4. **笔记**：原文保存与编辑、时间线；关键词/时间/类型筛选；从笔记创建待办或“以后想做”，并保留关联。
5. **语音与 AI**：Android 在线语音转文字；一个智能文本入口；仅接入由平台统一管理的 **OpenAI GPT**，用于账目/待办建议；所有 AI 结果均需用户确认；关闭 AI 后，三项记录的手动路径仍完整可用。

**明确延期到 V1 后：**

- 多模型供应商并行、模型切换与故障转移、运营模型控制台；
- 浏览器语音输入和离线语音转写；
- 复杂同步冲突的人工合并界面；
- 正式账户余额、账单导入、预算、转账、对账；
- 高级财务洞察与 AI 财务建议；
- 复杂笔记标签、语义搜索和 AI 问答；
- 自由拼装小组件；
- 历史版本浏览、数据导出和账号删除自动化等数据治理增强能力；其中 V1 不提供数据导出，Alpha 后再基于用户实际需求确定导出范围与格式。

### V1 AI 模型服务（已确认：方案 A）

V1 只接入 **OpenAI GPT**，并由平台统一管理。普通用户不需要、也不能选择底层模型供应商。V1 的目标是验证“AI 整理是否节省记录时间且结果可信”，而不是建设多模型平台。

当调用失败、结果不可靠或用户关闭 AI 时，产品必须回到完整的手动记录与确认路径，不能阻断待办、账目或笔记的保存。DeepSeek、豆包等国内模型的接入、人工切换、自动故障转移和成本路由均留到 V1 后，并仅在真实使用数据证明需要时评估。

### V1 Alpha 的 AI 使用保护（已确认：方案 B）

V1 只面向受邀账号开放 Alpha。平台为每个账号设置相对宽松的**每日智能整理请求上限**，同时为整个 Alpha 设置总用量上限、成本告警和可立即关闭 AI 的紧急开关。产品应记录每位试用者的实际调用量与结果确认/修改情况，但不向用户引入订阅、充值、积分或额度购买机制。

用户达到当天上限时，应明确提示“今天的智能整理次数已用完；你仍可继续手动记录，明天恢复”。AI 限制、调用失败或平台临时关闭 AI 均不得影响待办、账目或笔记的手动保存、同步与回顾。

### V1 删除与恢复最低保障（已确认：方案 B）

V1 中，待办、账目和笔记删除后必须进入统一回收站，默认保留 **30 天**。用户可在回收站恢复内容，或自行选择立即永久删除；V1 不提供复杂的历史版本浏览。

V1 不实现完整的自助账号删除自动化流程，但设置页必须提供清晰的“申请删除账号和数据”入口，并说明由平台人工受理。受理后应立即停用账号、撤销全部设备会话、停止同步和 AI 处理；申请在 **30 天** 撤销期结束后清理可识别账户与业务数据，并按公开说明处理备份残留。

### V1 Alpha 账号准入（已确认：一次性邀请码）

V1 Alpha 不开放普通注册。平台管理员通过管理后台按需为每位受邀试用者生成一枚**一次性邀请码**；用户使用邀请码完成邮箱验证和注册后，该邀请码立即失效，不能再次注册或转交他人使用。管理后台至少承担邀请码的生成、停用和重发；其余运营能力是否纳入 V1，仍需单独确认。

邀请制 Alpha 可先从 3–5 位相似用户开始。在没有内容丢失、跨账号数据泄露或关键同步可靠性问题后，管理员可以继续分批生成邀请码，将试用扩大到数十或数百人；扩容不等于直接开放普通注册。

当 Alpha 结束并准备扩大范围时，平台可以整体停用邀请码校验，切换为普通注册；邀请码不是长期账号体系的一部分。

### V1 运营管理后台（已确认：方案 B，按 V1 边界收敛）

V1 提供仅供平台管理员使用的运营管理后台。除一次性邀请码外，后台至少包含：

1. 管理员登录；
2. 查看 Alpha 用户的基本状态（邮箱、注册时间、是否已停用）并手动停用或恢复账号；
3. 查看每位用户的 AI 调用量、失败率、结果确认率和修改率，以及 Alpha 整体 AI 用量；
4. 查看和人工处理账号删除申请的状态；
5. 保留管理员生成/停用邀请码、停用/恢复账号、处理删除申请等操作的基础审计记录；
6. 查看受控的项目运行日志，特别是 AI 调用失败、超时、限流和结果处理错误。

### 日志与 AI 诊断快照（已确认：方案 B）

默认运行日志采用严格脱敏：可记录时间、环境、服务名、接口/操作、请求关联 ID、匿名化用户 ID、错误码与堆栈、AI 模型名、调用耗时、请求/响应大小、token 用量、错误类别和重试次数；不得记录笔记正文、待办内容、账目备注、密码、令牌、完整敏感请求内容或完整 AI 输入输出。

仅当用户主动使用“智能整理”，且发生 AI 调用失败或结果无法解析时，系统可保存一份**受控诊断快照**。快照必须是必要上下文的脱敏和长度截断版本，默认保留 **7 天**后自动删除；笔记正文默认不得进入快照，账目和待办也优先只保留结构化失败信息。查看诊断快照应使用更严格的管理员权限，每一次查看都必须写入审计记录。

此处“方案 B”不推翻已确认的 V1 AI 边界：V1 仍只接入并使用平台统一管理的 OpenAI GPT，不在后台提供多模型供应商、模型切换、自动故障转移或成本路由。

## 13. Alpha 验证与迭代门槛（已确认：方案 B）

V1 是否进入下一轮迭代，采用“安全底线 + 行为证据 + 用户访谈”的组合判断，而不是只看主观好评、注册量或付费。

### 不可妥协的安全与可信底线

- 不出现已确认且无法恢复的用户内容丢失；
- 不出现跨账号数据泄露；
- 不出现对笔记正文、账目金额或待办时间的静默篡改；
- 关键同步失败可被用户看见，并允许重试。

出现上述问题时，应优先修复可靠性，而不是扩大试用范围或增加功能。

### 需要收集的行为与价值证据

- 用户是否完成“Android 记录 → 同账号同步 → Web 整理或每周回顾 → 回到 Android 查看重点或继续行动”的跨端闭环；
- 待办、记账、笔记三项能力是否均被真实使用，并在第二周后仍有人持续使用；
- 是否有人通过每周回顾重新处理原本会沉底的计划或未完成待办；
- 是否有人能从收支回顾中说出具体发现；
- AI 建议的直接确认或轻微修改后确认比例，以及用户是否频繁关闭 AI；
- 试用者是否愿意继续使用，并能具体说明产品帮其避免的遗忘、重新发现的计划或获得的收支认识。

邀请制 Alpha 可以从 3–5 位用户起步，并在可靠性通过后扩大到数十或数百位用户。不同规模下的最低人数、比例与扩容门槛需要在确定测试策略后单独设定；但 AI 表现一般不能单独否定产品，只要手动记录与回顾闭环仍具价值。

### 分阶段扩容（已确认：方案 B）

邀请制 Alpha 采用“小范围稳定验证 → 分批扩大 → 每阶段复核”的节奏。首批 3–5 位用户只是最小验证组，不构成人数上限；当核心闭环、可靠性与运营能力通过当前阶段验证后，可以在保持一次性邀请码机制的前提下，分批扩大至 20–30 人、100 人，并根据容量与支持能力扩展到数百名受邀用户。

每一阶段至少稳定验证 14 天。进入下一阶段前，必须同时确认：无不可恢复的内容丢失、跨账号数据泄露或静默篡改；关键同步、认证和 AI 失败对用户可见、可重试且可诊断；AI 用量与成本仍在预设预算内；管理员的人工支持负荷仍可承受；并且有真实用户完成跨端闭环或证明单端使用价值。如果出现安全底线事故、系统性同步或认证故障、无法控制的 AI 成本异常或支持已明显超载，应暂停扩容，先止损、修复与复核。

### 开源策略（已确认：方案 B）

V1 的邀请制 Alpha 及其早期分阶段扩容期间，产品代码保持私有，优先验证可靠的记录、同步和回顾闭环，而不把开源社区运营、许可证选择、贡献治理、部署文档或自托管支持引入 V1 的关键路径。

当 V1 已完成 Alpha 闭环验证、核心安全与可靠性风险得到控制后，再单独决定是否开源以及采用的许可证。开源不是 V1 的发布承诺，也不自动等同于开放官方托管服务注册。即使未来开源，官方托管服务仍可独立维持邀请制或另行确定注册策略；任何公开仓库都不得包含生产密钥、用户数据、生产环境配置、内部日志或敏感运维资料。
