> **Trellis 状态：规划中，等待评审。**  
> 本文是任务 `08-13-personal-productivity-v1` 的 V1 需求基线。需求来自 `docs/product-exploration.md` 的已确认产品探索结论；若两者有冲突，以本文为准。**本 task 负责产品需求、范围、验收和影响可行性的高层技术约束，不负责代码级方案、完整接口字段、视觉 UI 或编码规范的最终定稿。**本文获用户批准并完成后，才可启动后续实施任务；当前不得创建业务源代码或启动实施任务。

## 1. 目标与用户价值

### 1.1 要解决的问题

普通备忘录擅长按时间记录，却容易让早期的计划沉入时间线；用户在事务繁多时虽能随手记下事情，却不一定有机会重新看见、判断或处理它。零散记账也不足以稳定地帮助用户理解自己的收入与支出。

本产品是独立的跨平台个人效率与个人财务管理应用，不依赖、不接入、也不同步小米备忘录。它帮助用户：

1. 随时安全记录待办、账目和笔记；
2. 每天看到当前重点；
3. 每周对旧计划做推进、保留、暂缓或放弃的取舍；
4. 从**已记录**账目中理解钱从哪里来、花到哪里去。

### 1.2 产品承诺

> 用户可随时安全记录；每天能看到重点；每周能做出取舍；并能从已记录账目中理解自己的收支去向。

最核心的承诺是：

> **每周回顾并做决定，而不是逼用户完成所有旧计划。**

“暂缓”和“不再需要”是积极、正常的结果。系统只能提出回顾和建议，未经用户同意不得把“以后想做”自动排入日程。

### 1.3 V1 目标用户和验证周期

- 首批用户：以 Android 为主、在碎片时间记录个人计划、临时想法和日常收支，并愿意使用桌面 Web 集中整理或回顾的个人用户。
- 账户边界：个人私有数据 + 同账号多设备同步；不含协作或共享。
- 发布方式：邀请制 Alpha，从 3–5 人起，稳定验证至少 14 天后按门槛扩容至 20–30 人、100 人和后续数百名受邀用户。
- 初步验证周期：约 4 周；验证真实闭环和可靠性，不以“功能齐全”或注册数作为成功标准。

### 1.4 核心循环

```text
Android 快速捕捉
  → 同账号同步
  → Web 集中整理 / 周回顾 / 收支回顾
  → Android 查看重点并继续行动
```

Android 是“随手记录与当下行动端”；Web 是“集中整理、规划与数据回顾端”。两端都可完成核心数据操作，但复杂分析、搜索筛选和批量管理优先在 Web 深化。

## 2. V1 范围与不可妥协规则

### 2.1 三个独立业务系统

```text
独立产品
├─ 待办系统
│  ├─ 已安排 / 今日行动
│  └─ 以后想做
├─ 记账系统
└─ 笔记系统
```

三者共享快速捕捉体验，但不合并成一个不清晰的“万能记录列表”。三项均是 V1 的一等能力，各自必须有一条不依赖 AI 的可靠手动路径。

### 2.2 全局不可妥协规则

| 编号 | 规则 |
| --- | --- |
| G-01 | 所有业务数据以认证账号为服务端权威归属边界；不得信任客户端提交的用户 ID。 |
| G-02 | 无论 AI、网络、语音转写是否可用，用户都能先安全保存文本内容；联网后完成同步和可选 AI 整理。 |
| G-03 | 笔记正文只能由用户编辑；AI 不得改写、删减、覆盖或自动摘要为正文。 |
| G-04 | AI 只产生建议草稿，不能直接写入正式待办、账目或笔记；需要用户确认或明确选择手动保存。 |
| G-05 | 无法判断的智能输入必须保留原始文本，进入待确认收件箱，不能强制归类。 |
| G-06 | 同步冲突不得静默覆盖笔记正文、账目金额或待办时间；必须保留可选版本并进入待处理冲突。 |
| G-07 | 待办、账目和笔记删除后进入 30 天回收站；用户可恢复或立即永久删除。 |
| G-08 | 运行日志、审计和第三方调用诊断默认不得成为用户正文副本；密码、令牌和完整敏感请求/响应绝不写入日志。 |
| G-09 | 普通用户不能选择、配置或切换底层模型提供商；V1 由平台统一管理。 |
| G-10 | 系统的收支统计和变化提示只描述“已记录账目”，不声称覆盖全部真实资产或消费。 |

### 2.3 V1 明确不做

- 小米备忘录插件、导入、同步或反向写入；
- 多人协作、共享待办、家庭账本、团队空间；
- 项目管理（子任务、依赖、时间块、甘特图）、复杂日历双向同步；
- 正式资金账户、余额、转账、对账、预算、自动银行流水、投资、多币种；
- 图片/文件附件、OCR、富文本、笔记本/文件夹、语义搜索、AI 问答检索；
- 永久音频存档、语音唤醒、方言、连续长录音；离线阶段的新录音转文本；Web Alpha 的完整浏览器语音输入链路；
- 自动排期“以后想做”、对普通笔记主动提醒、价值判断式消费诊断；
- 普通注册、OAuth/Passkey、支付、订阅、用户自选模型、多模型自动故障转移或成本路由；
- 数据导出、完整历史版本浏览、自助自动账号删除；
- 开源发布、许可证和自托管支持。Alpha 及早期扩容阶段代码保持私有。

## 3. 功能需求

### 3.1 账户、认证与设备（AUTH）

| 编号 | 需求 |
| --- | --- |
| AUTH-01 | Alpha 只允许管理员生成的一次性邀请码注册。邀请码在用户完成邮箱验证和注册后立即失效；可被管理员停用或重发。 |
| AUTH-02 | 支持邮箱/密码注册、邮箱验证、登录、登出、找回/重设密码。普通注册开关在 Alpha 结束后才可整体启用。 |
| AUTH-03 | 用户可查看自己的已登录设备会话并撤销指定会话；账号停用或删除申请受理时必须撤销全部会话。 |
| AUTH-04 | 用户仅能访问自己的业务数据、草稿、偏好、回收站和同步变更；管理员只能在后台访问规定的管理元数据和受控日志。 |
| AUTH-05 | 管理员可查看 Alpha 用户的基本状态、手动停用或恢复账号，并对邀请码、账号状态和删除申请操作形成审计记录。 |

### 3.2 待办与“以后想做”（TODO）

| 编号 | 需求 |
| --- | --- |
| TODO-01 | 待办至少包含：简洁行动表述、状态、优先级（高/普通/低）、计划时间（可空）、截止时间（可空）、来源和创建/更新时间。新建默认普通优先级。 |
| TODO-02 | “以后想做”是待办模块内的独立状态/类型，用于未承诺具体行动时间的愿望或计划；它不能被系统自动排期、自动催促或自动转为日程。 |
| TODO-03 | 用户能创建、编辑、完成、重新打开、删除和恢复待办；所有变更可跨设备同步。 |
| TODO-04 | 今日重点默认排序：已逾期 → 今日有计划或截止时间 → 未排期高优先级 → 普通 → 低。界面必须显示该条被推荐的原因。 |
| TODO-05 | 每周回顾支持：处理未完成待办（安排、延期、放弃）、处理“以后想做”（推进、保留、以后再看、减少出现、不再需要）、选择下周 1–3 件重要事项。 |
| TODO-06 | “以后想做”回顾推荐采用透明规则 + 轻量轮换 + 用户控制：近期想推进优先、较久未回顾轮换展示、以后再看/减少出现降低频率、不再需要后归档不再推荐；每条推荐说明原因，用户可替换、搜索加入或调整可见度。 |
| TODO-07 | 回顾窗口可由用户调整。窗口到达时只温和提醒一次；用户跳过后只保留首页轻提示并自动并入下次，不把跳过视为失败。 |
| TODO-08 | 只提醒用户明确设置计划时间或截止时间的待办；用户可关闭提醒和设置通知时段。 |

### 3.3 记账与收支回顾（LEDGER）

| 编号 | 需求 |
| --- | --- |
| LEDGER-01 | 已确认账目至少包含：收支方向、金额、发生时间、分类、备注；支付方式可选。金额必须精确存储，禁止以浮点数作为业务金额真相。 |
| LEDGER-02 | 提供少量清晰的内置分类，并允许用户建立和维护个人自定义分类；AI 只能建议，用户确认后才成为正式分类。 |
| LEDGER-03 | 支付方式仅为账目属性（如现金、微信支付、支付宝、银行卡、信用卡），不是账户、余额或转账体系。 |
| LEDGER-04 | 用户能创建、编辑、删除、恢复、按时间/方向/分类筛选账目，并查看日、周、月收入、支出、结余及分类汇总。 |
| LEDGER-05 | 周回顾可展示本周收入、支出、结余和主要消费去向。 |
| LEDGER-06 | “值得查看的收支变化”仅由透明、非评判性规则生成；每条必须说明仅基于已记录账目、对比范围和触发原因。数据不足时不提示，用户可关闭。禁止使用“异常、浪费、不合理”等价值判断。 |

### 3.4 笔记与找回（NOTE）

| 编号 | 需求 |
| --- | --- |
| NOTE-01 | 笔记正文是用户输入或确认后的原始文本；保存、编辑和同步不得由 AI 自动改写。 |
| NOTE-02 | 笔记可有标题、类型、轻量标签、收藏和“稍后回顾”等元信息；元信息不得替代或修改正文。 |
| NOTE-03 | 支持创建、编辑、删除、恢复、时间线浏览，以及标题/正文关键词、时间范围、类型、收藏和稍后回顾筛选。 |
| NOTE-04 | 用户从笔记创建待办或“以后想做”时，系统创建新的待办并保留原笔记正文；两者建立双向关联。 |
| NOTE-05 | 只有用户主动请求时，AI 才可对当前笔记建议标题、类型、标签或行动项；默认写笔记不调用模型。 |

### 3.5 快速捕捉、AI 整理与待确认收件箱（CAPTURE / AI）

首页同时提供明确入口和智能快速入口：

```text
[记一笔] [加待办] [写笔记]
[语音 / 文本智能快速记录]
```

| 编号 | 需求 |
| --- | --- |
| CAP-01 | 明确入口“记一笔”和“加待办”允许用户提交当前文本获取字段建议；用户可编辑、确认或放弃建议。 |
| CAP-02 | 明确入口“写笔记”默认原样保存，默认不把正文发送给 AI。 |
| CAP-03 | 智能快速记录只在用户主动触发“智能整理”时，把当前文本交给模型；模型建议待办、账目、笔记或无法判断。 |
| CAP-04 | 无法明确判断、AI 失败、结果不符合结构校验或用户暂不决定时，系统创建待确认收件箱项目，保留原始文本和有限候选信息；用户能稍后手动转换为任一业务类型或删除。 |
| AI-01 | V1 只接入平台统一管理的 OpenAI 模型服务。模型调用失败、达到配额、平台关闭 AI 或用户关闭 AI 时，不得阻断手动记录、同步、回顾和回收站。 |
| AI-02 | 模型只能收到处理当前动作所必需的内容：记账/待办为本次文本；笔记仅在用户明确请求辅助时发送当前笔记。不得持续发送完整历史原文。 |
| AI-03 | 个性化只能使用服务端保存的、来自用户已确认结果的结构化偏好规则。用户可查看、修正、关闭和清除该偏好；第三方模型只接收最小必要偏好上下文。 |
| AI-04 | 每位 Alpha 用户有相对宽松的每日智能整理上限；平台有总用量上限、成本告警和 AI 紧急关闭开关。达到上限时清晰提示手动路径仍可用；不做付费、充值或积分。 |

### 3.6 Android 语音输入（VOICE）

| 编号 | 需求 |
| --- | --- |
| VOICE-01 | Android 在线时支持普通话和英语录音转写。V1 采用平台统一管理的单一 OpenAI 转写服务，并在服务端保留小型 `TranscriptionProvider` 可替换接口；不实现第二提供商、自动故障转移或模型路由。 |
| VOICE-02 | 开始转写前，录音只有一份：保存于 Android 应用私有、加密的临时区；不进入同步数据库、不跨设备同步、不形成音频存档。 |
| VOICE-03 | 用户主动发起在线转写时，客户端上传音频，服务端只在本次请求处理期间流式转交转写提供商；服务端和第三方不得保留用于重试、同步或人工查看的副本。 |
| VOICE-04 | 转写文本必须先展示给用户查看、修改和确认。用户确认后才按所选入口进入笔记正文、智能整理草稿或手动业务表单。 |
| VOICE-05 | 网络或转写失败时，保留本地临时音频供用户在有效期内重试；也可放弃音频并转为手动文本草稿。V1 不承诺离线把新录音转成文本。 |
| VOICE-06 | 转写成功、用户取消或主动放弃时立即删除本地临时音频。未处理音频最多保留 24 小时，创建时显示确切到期时间；剩余 12 小时、1 小时如用户允许通知则发本地通知，否则持续显示应用内待处理状态。 |
| VOICE-07 | 到期未处理的音频自动、不可恢复地删除，仅保留不含音频和转写文本的状态提示。该临时音频不进入 30 天业务回收站。 |
| VOICE-08 | Web Alpha 不要求完整浏览器语音输入；Web 必须支持编辑已转写/已同步的文本。 |

### 3.7 平台体验、回收与账号删除（PLATFORM）

| 编号 | 需求 |
| --- | --- |
| PLAT-01 | Android 今日概览突出快速入口、重点待办、今日进度和基础收支；Web 提供可操作的数据工作台、搜索筛选、每周回顾、财务分析和设置，而非复制 Android 布局。 |
| PLAT-02 | Android 小组件 V1 提供一个预设基础模板，可按允许配置展示高优先级待办、待办数量、当日/当月收入和支出等数据。默认隐藏待办标题和财务金额；首次添加时必须做隐私展示引导。 |
| PLAT-03 | Android 离线时可保存文本、编辑操作和待同步工作；必须显示待同步、同步失败与可重试。Web 不承诺离线编辑。 |
| PLAT-04 | 待办、账目、笔记删除进入统一回收站，默认 30 天；用户可恢复或立即永久删除。 |
| PLAT-05 | 设置页提供“申请删除账号和数据”入口。人工受理后立即停用账号、撤销全部设备会话、停止同步和 AI；用户有 30 天撤销期，届满后清除可识别账户和业务数据，并按公开备份周期清理残留副本。 |

### 3.8 运营后台、日志与审计（ADMIN / OPS）

| 编号 | 需求 |
| --- | --- |
| ADMIN-01 | 管理后台包含管理员登录、邀请码生成/停用/重发、Alpha 用户状态管理、AI 用量与效果指标、账号删除申请处理、管理员操作审计及受控运行日志。 |
| ADMIN-02 | 后台默认不展示用户笔记正文、待办正文、账目备注或完整 AI 输入/输出；管理员查看用户状态所需邮箱属于受控个人信息。 |
| OPS-01 | 运行日志可包含时间、环境、服务/接口、关联 ID、匿名用户 ID、错误码/堆栈、模型名、耗时、请求/响应大小、token、错误类别和重试次数；不得包含密码、令牌、正文、备注或完整敏感请求/响应。 |
| OPS-02 | 仅当用户主动使用智能整理且 AI 调用失败或结果无法解析时，可保存脱敏、截断的诊断快照，默认 7 天自动删除。笔记正文不得进入快照；查看需要更高管理权限并写审计记录。 |

## 4. 安全、数据所有权与可靠性要求

### 4.1 安全基线

- 全部客户端/API/第三方调用使用 TLS；服务端仅接受受控来源、大小和 MIME 校验后的音频请求。
- 密码仅保存为强哈希；访问会话可撤销、可按设备管理；认证、上传和 AI 请求均须限流。
- 在数据库加密卷和加密备份之外，对用户正文、账目备注、金额、邮箱、偏好及模型建议使用应用层信封加密；密钥不得与密文一同以明文方式保存。
- 搜索和统计所需的最小非敏感索引、枚举、时间、归属和加密检索令牌可以分离保存，但不得把正文复制到日志、普通分析表或明文搜索索引。
- 所有管理敏感操作、诊断快照查看和删除处理写入不可篡改倾向的审计记录。

### 4.2 同步与冲突

- Android 离线工作区必须持久保存本地文本和操作队列；每次写入带稳定客户端操作 ID，服务端幂等处理。
- 客户端先推送本地操作、再拉取变更游标后的服务端变更；同步可重复执行而不产生重复正式数据。
- 并发编辑发生版本不匹配时，服务端保留服务端版本和客户端提交版本，创建待处理冲突；原正式记录不被静默替换。
- 用户在 Android 或 Web 选择保留某个版本或手动合并后，系统才创建新的权威版本并同步至其他设备。

### 4.3 Alpha 不可妥协底线和扩容门槛

任何阶段出现以下情况，都必须暂停扩容并先修复：已确认且不可恢复的内容丢失、跨账号数据泄露、笔记正文/账目金额/待办时间的静默篡改、系统性同步或认证故障、失控 AI 成本或明显超载的人工支持。

进入下一规模阶段前，至少稳定运行 14 天，并同时证明：安全底线未被触发；关键失败可见、可重试、可诊断；AI 成本在预算内；支持负荷可承受；真实用户完成跨端闭环或证明单端价值。

## 5. 验收标准

### 5.1 用户闭环

- [ ] 受邀用户可完成邮箱验证、注册、Android 和 Web 登录，并且同一账号数据隔离正确。
- [ ] 用户可在 Android 离线创建文本待办、账目和笔记；联网后能看到同步状态并完成可靠同步。
- [ ] 用户在 Android 创建的待办、账目、笔记可在 Web 查看、编辑和删除；删除后可在 30 天内恢复。
- [ ] 用户能在 Android 今日概览/小组件看到可解释的重点，在 Web 完成一次每周回顾并对事项做取舍。
- [ ] 用户能在 Web 看到已记录账目的日/周/月汇总与分类汇总，且所有表述清楚限定为已记录数据。

### 5.2 内容正确性与 AI 降级

- [ ] 所有账目在正式保存前可由用户确认和修改；金额精确且分类/时间/方向有效。
- [ ] 所有待办在正式保存前可由用户确认和修改；今日排序符合 `TODO-04`。
- [ ] 笔记正文从输入/转写确认到保存、同步、检索全过程不被 AI 自动改写。
- [ ] 智能快速记录无法判断、AI 超时、限流或输出无效时，原始文本仍进入待确认收件箱或手动保存路径。
- [ ] AI 关闭或配额耗尽后，三个业务域仍可完整手动记录、同步、回顾和删除恢复。

### 5.3 语音、同步与数据保护

- [ ] Android 语音成功时，用户先看到可编辑转写文本；确认后才保存业务文本；录音按规则删除。
- [ ] 转写失败时，临时录音可在 24 小时内重试或放弃；到期删除且不进入回收站；服务端不存在可供人工查看的音频副本。
- [ ] 两个设备并发修改同一内容时，敏感字段不会静默覆盖；用户能找到并解决冲突版本。
- [ ] 回收站、立即永久删除、账号删除申请、账号立即停用和 30 天撤销期均有可验证状态。
- [ ] 日志和受控诊断快照不包含禁止保存的正文、备注、密码、令牌或完整 AI 输入输出；查看受限快照有审计记录。

### 5.4 后台与运营

- [ ] 管理员可生成、停用和重发一次性邀请码；成功注册的邀请码不能再次使用。
- [ ] 管理员可查看脱敏运行日志、AI 错误和用量/确认/修改指标，但不能默认查看用户正文。
- [ ] 每用户每日 AI 限额、全局上限、告警和紧急关闭可测试；限制触发不影响手动路径。

## 7. 规划结论与实施前条件

- 本 PRD 没有阻塞性产品范围问题；技术决策 **TQ1 已确认**：服务端采用 **Go 模块化单体 + PostgreSQL**，按认证、同步、收件箱、待办、记账、笔记、回顾、AI/语音和后台等领域模块组织；V1 不拆分微服务。
- 技术决策 **TQ2 已确认**：Android、Web 用户端和管理后台统一使用版本化 **REST API + OpenAPI** 契约；V1 不引入 GraphQL、RPC 或 gRPC。
- 技术决策 **TQ3 已确认**：PostgreSQL 的 Go 数据访问采用 `pgx`、版本化 SQL migrations 与 `sqlc` 类型安全查询代码；核心业务不以 ORM 作为主要数据访问层，跨多个业务状态的写入必须使用显式事务。
- 在线转写的 V1 技术结论为**单一 OpenAI 转写服务 + 小型 `TranscriptionProvider` 可替换接口**，不引入第二提供商、自动故障转移或模型路由。
- 具体模型 ID、API 密钥、邮件供应商、部署地域、KMS/密钥服务和备份轮换由部署配置确定，不改变本产品边界；在 Alpha 上线前必须记录实际值、故障处置方式和公开的数据删除/备份说明。
- 在用户明确评审并批准 `prd.md`、`design.md`、`implement.md` 前，任务保持 `planning`，不得执行 `task.py start`，不得创建应用业务代码。
