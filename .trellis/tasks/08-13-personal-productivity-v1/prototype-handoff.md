## 1. 接手 AI 的目标

请为本产品设计：

1. Android、桌面 Web 用户端、Web 管理后台三端信息架构；
2. 核心用户流程；
3. 低保真线框图；
4. 使用模拟数据的可点击原型；
5. 正常、空状态、离线、失败、冲突、删除和无权限等状态；
6. 原型中发现的需求矛盾、待验证假设与设计取舍。

优先验证核心闭环，不追求第一轮覆盖所有页面：

```text
Android 快速捕捉
→ 显示本地保存和同步状态
→ Web 集中整理 / 每周回顾 / 收支回顾
→ Android 查看今日重点并继续行动
```

原型不得连接真实模型、语音服务、邮箱或生产数据库。

## 2. 产品定位

这是一个独立的、多用户、跨设备同步的个人效率与个人财务管理应用，**不是小米备忘录插件**，也不导入、不反向同步小米备忘录。

产品包含三个同等重要但彼此独立的系统：

```text
个人效率与个人财务管理应用
├─ 待办
│  ├─ 已安排 / 今日行动
│  └─ 以后想做
├─ 记账
└─ 笔记
```

三个系统共享快速记录体验，但不能合并成一个语义不清的“万能列表”。

### 产品承诺

> 用户可随时安全记录；每天能看到重点；每周能做出取舍；并能从已记录账目中理解自己的收支去向。

### 核心价值

> 每周回顾并做决定，而不是逼用户完成所有旧计划。

“继续保留”“以后再看”“减少出现”“不再需要”都是正常、积极的结果。系统不得未经用户确认，自动把“以后想做”排入日程。

---

## 3. 目标用户与 Alpha 边界

首批用户是以 Android 为主要随身设备的个人用户。他们会在碎片时间记录：

- 近期需要处理的事情；
- 暂时没有时间、但以后想做的计划；
- 临时想法和原始笔记；
- 日常收入和消费。

他们愿意在桌面 Web 上进行更集中、更复杂的整理与回顾。

账号和发布规则：

- 数据默认个人私有；
- 同一账号支持多设备同步；
- V1 不支持协作、共享待办或家庭账本；
- Alpha 使用管理员生成的一次性邀请码；
- 邀请码在用户完成邮箱验证和注册后立即失效；
- 后续可以关闭邀请码限制，改为普通注册；
- 初期可从少量用户开始，但设计目标是安全支持几十、上百乃至数百名受邀用户。

---

## 4. 三个平台的职责

### 4.1 Android：随手记录与当下行动端

主要承担：

- 文本快速记录；
- 在线语音转写；
- 创建待办、账目和笔记；
- 今日重点和完成待办；
- 离线文本保存；
- 待同步、同步失败和冲突提示；
- 桌面小组件；
- 必要的查看与编辑。

Android 首页应突出“立即记下”和“现在该做什么”，不应设计成复杂数据大屏。

### 4.2 Web 用户端：集中整理、规划与数据回顾端

Web 不能只是 Android 页面放大版，应采用桌面数据工作台式布局，主要承担：

- 待办集中整理；
- “以后想做”管理；
- 每周回顾；
- 收支数据看板；
- 搜索、筛选和批量整理；
- 笔记找回；
- 待确认收件箱；
- 同步冲突处理；
- 回收站和设置。

两端都能进行核心数据操作，但复杂分析与批量管理优先在 Web 深化。

### 4.3 Web 管理后台：受控运营端

管理后台与普通用户端分开，V1 主要承担：

- 一次性邀请码管理；
- 用户基本状态、停用和恢复；
- AI 用量、耗时、失败和效果指标；
- 账号删除申请处理；
- 管理员操作审计；
- 脱敏运行日志和 AI 错误诊断。

后台默认不得显示用户笔记正文、待办正文、账目备注、音频或完整 AI 输入输出。

## 5. V1 核心功能

### 5.1 待办

一条待办至少包含：

- 简洁行动标题；
- 可选说明；
- 状态；
- 优先级：高、普通、低，默认普通；
- 可选计划时间；
- 可选截止时间；
- 来源；
- 创建和更新时间。

待办模块包含两类内容：

1. **已安排 / 今日行动**：已有明确行动承诺；
2. **以后想做**：用户有兴趣或意愿，但尚未承诺时间。

#### 今日重点默认排序

1. 已逾期；
2. 今天有计划时间或截止时间；
3. 未排期但高优先级；
4. 普通优先级；
5. 低优先级。

界面必须展示推荐原因，例如“今天截止”“已逾期”“你标记为高优先级”。系统不能假装知道什么对用户最重要。

#### 每周回顾

每周回顾支持：

- 对未完成待办进行安排、延期或放弃；
- 对“以后想做”选择推进、继续保留、以后再看、减少出现或不再需要；
- 选择下周 1–3 件重要事项；
- 展示推荐出现的原因；
- 替换推荐项或搜索加入其他事项；
- 跳过时不使用失败或责备性表达。

系统只能建议，不能自动排期“以后想做”。

### 5.2 记账

一条正式账目至少包含：

- 收入或支出；
- 金额；
- 发生时间；
- 分类；
- 备注；
- 可选支付方式。

支付方式只是账目属性，例如现金、微信支付、支付宝、银行卡或信用卡。V1 不建立账户余额、转账和对账体系。

V1 支持：

- 少量内置分类；
- 用户自定义分类；
- 创建、编辑、删除和恢复；
- 按时间、收支方向和分类筛选；
- 日、周、月收入、支出和结余；
- 分类汇总；
- 每周收支回顾；
- 透明、非评判性的收支变化提示。

每条收支提示必须说明：

- 仅基于已经记录的账目；
- 使用了什么对比范围；
- 为什么出现这条提示。

不得使用“浪费”“异常”“不合理”等评价用户消费的表达。

### 5.3 笔记

笔记以用户原文为核心：

- AI 不得自动修改、删减、润色或覆盖正文；
- 支持标题、类型、轻量标签、收藏和“稍后回顾”等元信息；
- 支持时间线浏览；
- 支持按关键词、时间、类型、收藏和稍后回顾筛选；
- 可从笔记创建待办或“以后想做”；
- 转换后必须保留原笔记并建立双向关联。

只有用户主动请求时，AI 才能针对当前笔记建议标题、类型、标签或行动项。

#### 语音笔记流程

```text
录音
→ 转写文本
→ 用户查看和编辑
→ 用户确认
→ 确认后的文本原样保存为笔记正文
```

转写不是改写。AI 不能擅自重写笔记内容。

### 5.4 智能快速记录与待确认收件箱

Android 首页至少提供以下入口：

```text
[记一笔] [加待办] [写笔记]
[语音 / 文本智能快速记录]
```

- 从明确入口进入时，用户已经表达目标类型，AI 只负责字段提取和精简建议；
- 从智能快速入口进入时，AI 可以建议属于账目、待办或笔记；
- 正式待办和账目必须由用户确认后才创建；
- 笔记正文必须由用户确认，并按确认文本原样保存；
- 用户可以修改、拒绝或放弃建议。

当 AI 无法可靠判断、解析失败、结果未通过结构校验，或者用户暂时不决定时：

- 必须保留原始文本；
- 保存为待确认收件箱项目；
- 可以显示有限的候选类型和理由；
- 用户稍后可转换为账目、待办或笔记；
- 不能强制分类，也不能丢弃原文。

## 6. AI 与语音边界

### 6.1 AI

- V1 由平台统一接入 OpenAI；
- 普通用户不能选择 GPT、DeepSeek、豆包等底层供应商；
- 供应商替换属于服务端适配问题，不暴露给普通用户；
- AI 只生成建议草稿，不直接生成正式待办或账目；
- AI 失败、关闭或达到限额时，三个业务系统的手动路径仍必须可用；
- 待办和记账只发送当前一次输入；
- 笔记默认不发送，只有用户主动请求辅助时才发送当前笔记；
- 不持续向第三方发送完整历史原文；
- 个性化由本服务保存结构化偏好规则，用户可以查看、修正、关闭和清除；
- 发送给第三方的偏好上下文必须受控且最小化。

### 6.2 Android 在线语音

- V1 仅支持普通话和英语；
- 使用单一 OpenAI 在线转写服务；
- V1 不实现第二 ASR、自动故障切换或离线 ASR；
- Web Alpha 不要求浏览器语音输入；
- Web 可以编辑已经同步的转写文本。

#### 临时音频规则

1. 音频只存放在 Android 应用私有、加密的临时区域；
2. 不进入同步数据库，不跨设备同步；
3. 服务端只在当前请求中转，不保存音频副本；
4. 成功、取消或用户主动放弃时立即删除；
5. 失败后最多保留 24 小时供重试；
6. 创建时显示确切到期时间；
7. 剩余 12 小时和 1 小时时可按通知权限提醒；
8. 到期后不可恢复删除；
9. 临时音频不进入 30 天业务回收站。

原型必须包含转写失败后的选择：**重试、放弃音频并改为文本、取消**。

## 7. 离线、同步、冲突与错误处理

### 产品承诺

> 无论有没有网络，用户都能先把文本安全记下来；联网后再完成同步与可选的 AI 整理。

Android 必须明确显示：

- 已保存到本机；
- 待同步；
- 正在同步；
- 同步失败；
- 可重试；
- 冲突待处理。

以下冲突不得静默覆盖：

- 笔记正文；
- 账目金额；
- 待办计划时间或截止时间。

冲突界面应允许用户：

- 保留本机版本；
- 保留服务端版本；
- 手动合并后保存。

### 错误处理原则

- AI 失败：保留原文，允许手动填写或稍后重试；
- 转写失败：保留受时限保护的本地临时音频，允许重试或改为文本；
- 网络失败：先保存本地文本，再显示待同步；
- 表单校验失败：指出具体字段，不清空用户输入；
- 无法判断类型：进入待确认收件箱；
- 冲突：保留两个版本，不静默覆盖；
- 权限或账号停用：说明原因，停止继续同步和 AI；
- 删除操作：明确区分进入回收站和立即永久删除。

## 8. 删除、恢复、隐私与安全体验

### 业务数据删除

- 待办、账目和笔记进入统一回收站；
- 默认保留 30 天；
- 用户可以恢复；
- 用户可以立即永久删除。

### 账号删除

- 用户可以在设置中发起账号删除申请；
- 平台人工受理后立即停用账号；
- 撤销全部设备会话；
- 停止同步和 AI；
- 用户有 30 天撤销期；
- 到期后清除可识别账户和业务数据；
- 备份残留按公开周期清理。

### Android 小组件隐私

V1 提供一个基础模板，可配置显示：

- 最高优先级待办；
- 待办数量；
- 当天收入和支出；
- 当月收入和支出。

隐私规则：

- 默认隐藏待办标题；
- 默认隐藏具体财务金额；
- 首次添加小组件时必须做清晰的隐私引导；
- 用户明确确认后才能展示敏感内容。

### 日志和后台隐私

禁止记录或展示：

- 密码和令牌；
- 用户业务正文；
- 笔记正文；
- 账目备注；
- 音频；
- 完整 AI 输入输出。

AI 调用失败时可以保存脱敏、截断的诊断快照：

- 默认保留 7 天；
- 笔记正文不得进入快照；
- 只有更高权限管理员可以查看；
- 每次查看都要写入审计日志。

## 9. V1 明确不做

- 小米备忘录插件、导入、同步或反向写入；
- 多人协作、共享待办、家庭账本或团队空间；
- 子任务、依赖、甘特图等项目管理能力；
- 预算、账单导入、银行自动流水；
- 多币种、投资、正式账户余额和转账体系；
- 数据导出；
- 图片、附件、OCR、富文本；
- 笔记本、文件夹和复杂标签体系；
- 语义搜索和基于历史内容的 AI 问答；
- 离线语音识别；
- Web 浏览器语音完整链路；
- 多模型切换、模型市场和自动故障转移；
- 支付、订阅、充值、积分和套餐；
- 普通注册、OAuth、Passkey；
- 完整历史版本浏览；
- 开源、自托管和社区治理。

这些只属于 Alpha 后的候选池，不是 V1 承诺。

## 10. 原型必须覆盖的六条流程

### 流程一：以后想做与每周回顾

```text
Android 创建“以后想做”
→ 同步到 Web
→ 一周后进入回顾候选
→ 查看出现原因
→ 选择推进 / 保留 / 以后再看 / 减少出现 / 不再需要
→ Android 今日重点只显示用户主动推进的事项
```

### 流程二：AI 辅助记账

```text
输入“昨晚八点打车花了36.5元”
→ AI 建议：支出 / 36.50 / 昨晚20:00 / 交通
→ 用户修改或确认
→ 创建正式账目
→ Web 收支看板更新，并声明仅基于已记录账目
```

### 流程三：语音笔记

```text
Android 录音
→ 上传转写
→ 用户查看并编辑转写文本
→ 用户确认
→ 文本原样保存为笔记正文
→ AI 不自动改写
```

### 流程四：无法可靠分类

```text
输入“下个月考虑学游泳，预算可能500”
→ 系统无法可靠判断是待办、笔记还是账目
→ 保留原文进入待确认收件箱
→ 显示候选类型但不强制
→ 用户选择转为“以后想做”
```

### 流程五：离线记录与同步

```text
Android 离线创建笔记或待办
→ 立即显示“已保存到本机 / 待同步”
→ 网络恢复后同步
→ Web 出现同一原文
→ 两端同时修改敏感字段时进入冲突处理，而不是覆盖
```

### 流程六：AI 或语音失败

```text
AI 超时 / 达到限额 / 转写失败
→ 原始文本或临时音频仍在规定边界内安全存在
→ 显示清晰错误和下一步
→ 用户可以重试、改用手动表单或保存到待确认收件箱
```

## 12. 原型状态与文案要求

每个关键页面至少考虑：

- 初次使用与空状态；
- 正常有数据；
- 加载中；
- Android 离线；
- AI 不可用或达到限额；
- 同步失败；
- 数据冲突；
- 删除确认；
- 无权限或账号停用；
- 无搜索结果。

文案基调：

- 平静、清楚、不责备用户；
- 不使用“你又没完成”等压力表达；
- 不对消费进行道德评价；
- 清楚区分“AI 建议”和“已经正式保存”；
- 清楚说明数据是保存在本机、待同步还是已经同步；
- 对永久删除、音频过期和账号停用使用明确文案。

---

## 13. 原型不可违反的规则

1. 不把待办、记账和笔记合并成一个万能列表；
2. 不让 AI 未经确认直接创建正式账目或待办；
3. 不允许 AI 自动修改笔记正文；
4. 不自动安排或催促“以后想做”；
5. 无法判断类型时必须保留原文；
6. 财务提示不得评判用户消费；
7. 离线、同步失败和冲突必须有可见状态；
8. 小组件默认不得暴露待办标题和金额；
9. 普通用户不得选择底层模型供应商；
10. 不因 AI、语音或网络失败阻断手动记录；
11. 不让管理后台默认读取用户业务正文；
12. Android 与 Web 不得采用完全相同的页面布局。

## 14. 已确认的高层技术边界

| 领域 | 已确认选择 |

- 完整 OpenAPI 字段与错误码；

## 15. 原型验收标准

测试者应能在不听额外解释的情况下完成：

- 在 Android 快速记下一条内容，并知道是否已保存、是否已同步；
- 将 AI 建议修改后确认成正式账目；
- 将无法分类的原文放入待确认收件箱并稍后处理；
- 保存一条不被 AI 改写的语音笔记；
- 在 Web 完成一次“以后想做”的每周取舍；
- 看懂今日重点的推荐原因；
- 看懂收支看板仅基于已记录账目；
- 发现并处理一次跨设备冲突；
- 理解回收站删除与永久删除的区别；
- 理解小组件默认隐藏敏感数据的原因。

原型评审时重点记录：

- 哪一步让用户犹豫；
- 用户是否能区分“草稿建议”和“正式数据”；
- 用户是否相信内容不会丢失或被 AI 擅自修改；
- 每周回顾是带来帮助还是产生压力；
- Android 和 Web 的职责是否清楚；
- 哪些页面或功能可以继续从 V1 删除。
